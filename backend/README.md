# Backend

Backend SIMPEG menggunakan Go 1.27.4 (lihat `backend/go.mod`), GORM, dan PostgreSQL. `internal/models` memetakan tabel aplikasi yang dibuat oleh migrasi Goose di `migrations/`; migrasi SQL adalah sumber skema yang ditinjau dan diterapkan.

Gunakan `internal/database.OpenPostgres` agar nama tabel dan kolom mengikuti konvensi PostgreSQL yang dipakai migrasi. Model menyimpan foreign key sebagai kolom UUID; relasi untuk kebutuhan query dapat ditambahkan bersama fitur yang memakainya.

Kontrak HTTP/JSON MVP ditulis dalam OpenAPI 3.1 di `../docs/openapi.yaml`. Seluruh endpoint data berada di bawah prefix versi `/api/v1`; endpoint operasional (`/health`, `/ready`) tidak berversi. Grant runtime ada di `cmd/server/policy.go` (definisi tunggal di `internal/policymatrix`); status implementasi cakupan akses tidak boleh disimpulkan hanya dari kontrak endpoint. Sejak 16 November 2026 kontrak memuat **seluruh** operasi yang terdaftar di backend (**135 path, 231 operasi**, 0 rute hilang/ekstra, 0 `operationId` duplikat; direkonstruksi dari registrasi router 2026-11-15 lalu diperluas saat `DEC-088` (pensiun) dan `DEC-091` (baca SK)); setiap rute baru wajib didokumentasikan di `../docs/openapi.yaml` pada saat pendaftaran.

## Versi API

Versi API memakai prefix path: `/api/v1/employees`, `/api/v1/organizations`, dan seterusnya. Konstanta `httpserver.APIPrefix` dan `httpserver.Version` dipakai di route dan tes — jangan menulis path `/api/...` secara literal.

- Path `/api/...` tanpa versi ditolak `400 unversioned_path` dengan pesan yang memuat prefix yang benar.
- Path dengan versi yang tidak dikenal, misalnya `/api/v2/employees` saat ini versi `v1`, menghasilkan `404 not_found`.
- Setiap respons memuat header `X-API-Version`.
- Versi naik hanya bila ada perubahan yang merusak kompatibilitas. Perubahan additive tetap pada `v1`; versi lama tetap didukung selama masa transisi.

Endpoint operasional `/health` dan `/ready` berada di luar prefix versi.

Atur `DATABASE_URL` pada aplikasi yang memanggil backend dan berikan nilainya ke `OpenPostgres`. Migration runner yang dipilih adalah Goose dengan konfigurasi di `.goose.yaml`; workflow deployment tersedia di `.github/workflows/deploy-migrations.yml` (dipicu secara manual via `workflow_dispatch`, `DATABASE_URL` sebagai secret GitHub, belum pernah dijalankan di GitHub karena environment `staging`/`production` dan secret belum dibuat; urutan perintah diuji manual terhadap DB uji). Status migrasi per 2026-11-14: migrasi `000001`–`000023` diterapkan pada database produksi `postgres` dan database uji `simpeg_perf`; migrasi `000024_jabatan.sql` sudah ada dan diterapkan pada database disposable `simpeg_verify` (2026-11-13), **belum** pada produksi; migrasi `000025_payroll_core.sql` sudah disetujui (`DEC-068`, disetujui 2026-11-14) tetapi belum diterapkan pada database mana pun; migrasi `000026_mesin_absensi_pin.sql` (`DEC-077`, implementasi 2026-11-14) juga baru terdaftar di repo dan belum diterapkan pada staging/produksi (hanya pada database disposable lokal). Karena migrasi `000025`/`000026` sudah terdaftar di repo, `migrate up` pada target mana pun akan menerapkannya, jadi penerapannya wajib lewat workflow staging lebih dulu, lalu verifikasi `perfbench schema`, lalu produksi dengan persetujuan pemilik. Tinjau dan terapkan melalui proses migrasi yang disetujui sebelum memakai CRUD. Jangan menjalankan `AutoMigrate`.

## Struktur lapisan

Backend dibagi per area bisnis, dan tiap area memisahkan empat lapis:

| Lapis        | Isi                                                                                     | Aturan                                            |
| ------------ | --------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `domain`     | Aturan, validasi, dan nilai tanpa I/O.                                                  | Tidak mengimpor HTTP maupun database.             |
| `app`        | Use case: memeriksa permission, membatasi cakupan unit, lalu memanggil port repository. | Tidak menulis SQL dan tidak menulis respons HTTP. |
| `repository` | Port persistensi dan adapter GORM.                                                      | Satu-satunya lapisan yang menulis SQL.            |
| `httpserver` | Transport: dekode permintaan, panggil use case, petakan error ke status HTTP.           | Tidak memuat aturan bisnis.                       |

Area yang sudah dipisah: `internal/directory/{domain,app,repository}` (pegawai, unit organisasi, kategori, jejak audit), `internal/payroll/{domain,app,repository}` (slip gaji, konfirmasi pembayaran, jadwal gajian per unit), dan `internal/holiday` (kalender hari libur nasional). Kontrak daftar bersama ada di `internal/listing` (`listing.Options`, `listing.Page`).

## Mata uang dan zona waktu

Mata uang sistem adalah Rupiah Indonesia (IDR) dan tidak ada konversi antar-mata uang. Nominal diformat hanya lewat `internal/money`: `money.Format(1500000)` menghasilkan `Rp 1.500.000` (pemisah ribuan titik, desimal koma).

Zona waktu operasional adalah Asia/Jakarta (UTC+7, WIB). Penyimpanan timestamp memakai UTC: `database.OpenPostgres` memaksa parameter runtime `timezone=UTC` pada DSN sehingga default `now()` dan nilai yang ditulis GORM memakai basis yang sama. Konversi ke waktu lokal dilakukan saat tampilan dan aturan kalender melalui `internal/timeutil` (`timeutil.InLocation`, `timeutil.FormatDate`). Kolom tanggal pada skema acuan (`date`) menyimpan kalender tanpa jam; nilainya ditulis sebagai tengah malam UTC agar tanggal yang dibaca kembali tetap sama setelah dikonversi.

## Enkripsi kolom PII

Kolom `user.nik`, `user.nip`, `user.npwp`, `RiwayatPendidikan.noIjazah`, dan `KeluargaPegawai.nik` disimpan terenkripsi pada level aplikasi: AES-256-GCM dengan nonce acak per enkripsi, format `enc1:` + base64url. Setiap kolom berpasangan dengan blind index HMAC-SHA256 (`nikHash`, `nipHash`, `npwpHash`, `noIjazahHash`, `keluargaPegawai."nikHash"`) yang menegakkan pencarian kesetaraan (dan keunikan untuk kolom identitas pegawai). Konsekuensi operasional:

- Pencarian pegawai pada NIP dan pencarian keluarga pada NIK adalah **kesetaraan persis** (setelah normalisasi), bukan substring ILIKE; substring hanya berlaku untuk `nama`.
- Pengurutan kolom `nip`/`nik` tidak tersedia; sort pegawai memakai `nama`, `createdAt`, `updatedAt`, sort keluarga memakai `nama`, `tanggalLahir`, `statusTanggungan`, `createdAt`, `updatedAt`.
- Backend mendekripsi sebelum mengirim respons dan mengenkripsi saat menyimpan; kontrak HTTP tidak berubah. Tanpa `PII_ENCRYPTION_KEY`, jalur yang menyentuh kolom PII gagal dengan galat eksplisit (bukan nilai kosong).
- Kehilangan kunci membuat data PII tidak dapat dibaca; rotasi belum didukung. Buat dengan `openssl rand -base64 32` dan simpan salinan cadangan.
- Pencarian/log tidak pernah memuat nilai PII; blind index tidak dapat dibalik.

Detail: `DEC-053`, `DEC-054`, `docs/PRD.md` (Enkripsi kolom PII), migrasi `000022_pii_identity_encrypt.sql` dan `000023_keluarga_nik_encrypt.sql`.

## Autentikasi dan otorisasi

Endpoint `GET /api/v1/me` memerlukan `Authorization: Bearer <session-token>`. Backend mendukung dua jenis sesi: JWT Better Auth (diverifikasi signature HMAC dengan `BETTER_AUTH_SECRET`) dan sesi opaque pada tabel `session` yang ditolak bila kedaluwarsa; keduanya menghasilkan principal dari data server-side (identitas dan role). Token yang tidak valid menghasilkan `401`; endpoint tanpa autentikasi tidak memperoleh principal. `GET /api/v1/me` mengembalikan identitas sesi; bila layanan profil mandiri dipasang, respons ikut memuat `nama` dan `noHp` dari record user. `PATCH /api/v1/me` memungkinkan principal mengubah `nama` dan `noHp` miliknya sendiri (identifier selalu dari sesi, bukan body); perubahan dan jejak audit `profile.updated` ditulis dalam satu transaksi dan jejak tidak memuat nilai, hanya nama kolom yang berubah. Tidak ada endpoint untuk mengubah email, NIP, PII terenkripsi, role, atau unit (hendak administrator).

Middleware `RequirePermission` hanya mengizinkan grant eksplisit untuk nama role dan permission; grant yang tidak didefinisikan ditolak. `RequireAnyPermission` mengizinkan salah satu dari beberapa permission (dipakai pada route daftar/detail pegawai) dan tetap menolak bila tidak ada yang cocok. Matriks role disetujui dan dikonfigurasi secara statis di `cmd/server/policy.go` (definisi tunggalnya di `internal/policymatrix`, rinciannya ada di `../docs/PRD.md` §11). `auth.CanAccessUserInScope` menerapkan pemeriksaan self/homebase pada use case baca, ubah, dan arsip pegawai di lapisan aplikasi.

**RBAC scoped (`DEC-087`–`DEC-089`):** `internal/rbac` menambah evaluator berbasis _scoped assignment_ (`rbac_roles`, `rbac_permissions`, `rbac_role_permissions`, `rbac_user_role_scopes`, migrasi `000032`). `rbac.PolicyAdapter` membungkus grant statis: `AllowsScoped` (dipakai `RequirePermission`) mencoba evaluator lebih dulu — bila principal punya assignment, keputusan RBAC bersifat otoritatif (termasuk penolakan, sehingga RBAC dapat mencabut grant statis); tanpa assignment, grant statis dipakai sebagai migrasi bertahap. Aturan evaluator: assignment ber-scope tidak pernah mengizinkan permintaan `:any`; assignment tanpa scope mengizinkan `:any`; `deniedPermissions` (blacklist) menutup grant; tier superadmin/operator induk bypass matriks. Permission flat dipecah hanya lewat `rbac/domain.ParsePermission`. Perkakas `cmd/rbacseed` memetakan grant statis ke data RBAC untuk pengguna yang sudah ada (dry-run bawaan; `--apply` idempoten); prosedur lengkap ada di `../docs/RUNBOOK.md` §7A. Endpoint admin RBAC berada di `/api/v1/admin/rbac/*` (permission `rbac:read`/`rbac:manage`).

Backend tidak menyediakan login, OAuth callback, atau penerbitan sesi; autentikasi dijalankan runtime Better Auth di frontend. Endpoint `/api/v1/me` hanya memverifikasi sesi yang sudah ada. Endpoint `POST /api/v1/auth/logout` tersedia dan menghapus baris `session` sehingga token tidak lagi berlaku; logout bersifat idempoten. Endpoint ini hanya mencabut sesi opaque di database — penrevokasian token JWT milik Better Auth tetap dilakukan oleh runtime autentikasi. Endpoint `POST /api/v1/auth/session` hanya terdaftar bila `SessionIssuer` aktif; pemanggil wajib memakai sesi bearer valid dan permission `auth:session:issue` (admin). Dengan body `{userId}` boleh diserahkan, endpoint menerbitkan sesi bearer baru (token + `expiresAt`) dan mengembalikan `{userId, expiresAt, token}` dengan status `201`; role/homebase pada sesi baru diambil dari data server-side, sehingga token tersebut tidak dapat dipakai menaikkan peran. Provider autentikasi (Better Auth) dan matriks role sudah diputuskan, tetapi detail berikut masih harus ditetapkan dan diuji sebelum rilis: rotasi/revokasi sesi, CSRF/cookie, provisioning akun, dan MFA. Akun nonaktif dan sesi invalid ditolak. Jangan meneruskan `RoleName` atau identitas dari header selain sesi terverifikasi.

## Health, readiness, dan observability

`GET /health` adalah liveness: selalu `200` selama proses hidup, dan tidak gagal hanya karena dependency eksternal sedang tidak tersedia. `GET /ready` adalah readiness: memeriksa dependency wajib (saat ini ping PostgreSQL) dengan timeout dan mengembalikan `503` bila belum siap. Detail kegagalan tidak dikembalikan agar tidak membocorkan host, connection string, atau kredensial. Jangan menggabungkan kedua endpoint tersebut.

Log ditulis sebagai JSON satu baris per entri oleh paket `internal/observability`, dengan correlation ID pada header `X-Request-ID`. Request ID dari klien dipakai hanya bila karakternya aman; selain itu digenerate ulang. Header kredensial, body request, dan nilai query string tidak pernah dicatat. Log ditulis ke stdout, jadi pengelolaan dan retensinya mengikuti kebijakan deployment.

`GET /api/v1/admin/slo/metrics` (permission `slo:read`, admin saja, deny-by-default) mengembalikan ringkasan agregat metrik SLO pada jendela 24 jam (bawaan) atau maksimum 168 jam: jumlah permintaan, galat 5xx, laju galat, dan latensi rata-rata/p95/p99/maks, baik agregat maupun per rute. Isinya agregat per rute, bukan metrik mentah per jendela; `sloMetric` kosong (respons 200 dengan total nol) selama `SLO_ENABLED` belum menulis metrik. Halaman admin `/admin/slo` di frontend menampilkan data ini (`DEC-050`, kontrak di `../docs/openapi.yaml`).

`GET /api/v1/admin/ops/status` (permission `ops:read`, admin saja, deny-by-default) mengembalikan **agregat** status operasional antrean keluar (outbox): jumlah pesan per status (`pending`/`processing`/`done`/`failed`), waktu dan usia pesan tertua yang belum selesai, serta jumlah `failed` per jenis pekerjaan. Endpoint bersifat read-only dan **tidak** memuat payload pesan, dedupe key, alamat penerima, atau isi kredensial — hanya agregat untuk memantau backlog dan kegagalan notifikasi/pengiriman (`DEC-065`, kontrak di `../docs/openapi.yaml`, handler di `internal/httpserver/ops_handlers.go`, pembaca agregat di `internal/outbox`).

Pengumpulan metrik/log dan alerting di luar aplikasi: templat stack self-hosted ($0) ada di `../observability/` (Prometheus, Alertmanager, Grafana, Loki + Promtail, node-exporter, cAdvisor, blackbox-exporter, metrik RabbitMQ). Retensi log agregasi awal 30 hari, terpisah dari `AUDIT_RETENTION_DAYS` dan `SLO_RETENTION_DAYS` (`DEC-065`, `DEC-066`). Templat itu **belum terpasang di target produksi**; prosedurnya di `../docs/RUNBOOK.md` §9/§9A dan `../docs/backup-restore-drill.md`.

## Keamanan endpoint

`httpserver.CORSMiddleware` hanya memberi header CORS untuk origin yang tercantum di `TRUSTED_ORIGINS`; origin lain tidak mendapat akses lintas origin, dan preflight dari origin tak dikenal ditolak `403`. `httpserver.SecurityHeadersMiddleware` menambahkan `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy`, dan `Permissions-Policy` pada setiap respons. `httpserver.RateLimiter` membatasi permintaan per klien dengan batas lebih ketat pada endpoint autentikasi. `httpserver.StatementTimeoutMiddleware` membungkus context permintaan dengan batas waktu statement database.

## Integrasi layanan pendukung

Keempat integrasi diimplementasikan sebagai paket terpisah di `internal/`.

**Outbox persisten** (`internal/outbox`) adalah fondasi. Transaksi bisnis menulis baris outbox dalam transaksi yang sama sehingga pekerjaan tidak hilang saat queue eksternal gagal. Baris diklaim memakai `FOR UPDATE SKIP LOCKED`, kunci `dedupeKey` mencegah pengiriman ganda, retry memakai backoff eksponensial, dan pesan yang melewati batas percobaan diletakkan pada status `FAILED` sebagai dead-letter. Meja `outboxMessage` dibuat lewat migrasi `000006_outbox_message.sql`. Pembaca agregat (`outbox.StatsReader` → `outbox.Stats`) menghitung jumlah pesan per status, usia pesan tertua, dan kegagalan per jenis; agregat ini diekspos read-only lewat `GET /api/v1/admin/ops/status` (`ops:read`) tanpa payload/dedupe key/penerima (`DEC-065`).

**QStash** (`internal/qstash`) **tidak dipakai pada deployment mana pun** (`DEC-102`); paket ini tersisa hanya untuk kompatibilitas. Callback yang terdaftar: `POST /api/v1/internal/qstash/audit/cleanup` (retensi jejak audit, `audit.cleaned`), `POST /api/v1/internal/qstash/payroll/notify` (pemberitahuan slip gaji, `payroll.notified`), dan `POST /api/v1/internal/qstash/slo/evaluate` (pemeriksaan target SLO). Ketiganya **tidak** memakai sesi bearer; pengesahnya signature QStash. Ketiganya tidak dipanggil oleh penjadwal mana pun; pekerjaan tersebut berjalan lewat RabbitMQ.

**RabbitMQ** (`internal/mq`) adalah satu-satunya transport pekerjaan terjadwal — `DEC-042`, `DEC-102`. Bila `RABBITMQ_URL` diisi, server menjalankan konsumen pekerjaan (`mq.Consumer`); tidak ada pendaftaran jadwal eksternal. Payload dan kind sama dengan callback QStash (`{"kind": "audit.cleanup"}` dan seterusnya), sehingga logika pekerjaan identik. Penjadwal `cmd/jobsched` menerbitkan pesan persistent dari tick cron UTC dengan publisher confirm. Pesan yang gagal dijalankan pindah ke antrean `simpeg.jobs.dead` (dead-letter); tick berikutnya memicu eksekusi baru. Topologi (exchange, antrean, binding) dideklarasikan idempoten saat startup. Detail operasional ada di `rabbitmq/README.md` dan `docs/RUNBOOK.md` §8B.

**Migrasi** (`cmd/migrate`) membawa seluruh migrasi Goose dalam binary (embedded filesystem dari `migrations/migrations.go`) sehingga container migrasi tidak memerlukan CLI terpisah. `migrate` menerapkan migrasi yang belum jalan dan `migrate status` menampilkan statusnya; keduanya idempoten dan aman diulang.

**Email** (`internal/notify`) memakai SMTP. `notify.SalaryPaidNotice` tidak menerima parameter nominal — nominal gaji hanya tersedia di halaman terautentikasi dan dirujuk lewat tautan. `notify.EmailDeliverer` menjembatani antrean outbox ke SMTP: worker background mengirim pesan yang diklaim dispatcher. Kesalahan permanen (payload rusak, jenis tidak dikenal, sumber konfirmasi pembayaran belum dikonfigurasi) langsung menjadi dead-letter tanpa diulang; kegagalan sementara dijadwalkan ulang dengan backoff.

Alamat pengirim bawaan adalah `no-reply@simpeg.unisubang.ac.id` dengan origin aplikasi `https://simpeg.unisubang.ac.id`. Backend memvalidasi bentuk alamat pengirim saat start dan menolak alamat yang tidak sah.

**Sumber konfirmasi pembayaran sudah ada.** Modul penggajian menyimpan bukti pembayaran pada tabel `pembayaran` yang menempel pada slip gaji, dan slip ditandai `TERBAYAR`. `notify.EmailDeliverer.Confirmations` memakai `payroll/app.Service.ConfirmedPayment` sehingga notifikasi gaji hanya terkirim bila pembayaran benar-benar tercatat. Notifikasi gaji tetap tidak pernah memuat nominal.

**Redis** (`internal/cache`) hanya untuk cache data referensi. `ReadThrough` selalu memuat ulang dari sumber utama bila cache miss atau Redis gagal, sehingga cache tidak pernah menjadi sumber kebenaran. Kunci yang menyerupai sesi, token, kredensial, penggajian, atau status pembayaran ditolak saat runtime. Cache daftar kategori pegawai disambungkan ke `GET /api/v1/categories`; kalender hari libur disambungkan ke `GET /api/v1/holidays?year=` (`holiday:{year}`, TTL 24 jam). Tanpa Redis konfigurasi pembacaan tetap langsung ke PostgreSQL.

Penyimpanan objek S3-compatible belum masuk scope dan mekanismenya sengaja tidak dibuat.

## Format error

Semua endpoint memakai bentuk respons yang sama melalui paket `internal/apierror`:

```json
{"error": {"code": "...", "message": "...", "requestId": "...", "fields": {...}, "rows": [...]}}
```

`code` selalu ada; `message`, `requestId`, `fields`, dan `rows` bersifat opsional sesuai jenis error. Gunakan konstanta `apierror.Code*` dan jangan menulis bentuk error sendiri di paket lain. Respons `404` dan `405` yang dihasilkan router juga dikonversi ke bentuk JSON yang sama oleh `httpserver.JSONErrorMiddleware`.

## Direktori pegawai dan organisasi

CRUD pegawai tersedia di `/api/v1/employees`; organisasi tersedia di `/api/v1/organizations` untuk unit, fakultas, jurusan, biro, dan bagian. Semua jenis menggunakan satu pohon induk-anak fleksibel. `DELETE` mengarsipkan record, tidak menghapus riwayat; organisasi dengan pegawai aktif atau anak aktif tidak dapat diarsipkan. Perubahan direktori dicatat ke `AuditLog` tanpa menyalin nilai profil ke log.

Permission endpoint pegawai adalah `employee:read:any`, `employee:read:homebase`, `employee:read:self`, `employee:create`, `employee:create:homebase`, `employee:update:any`, `employee:update:homebase`, `employee:archive`, `employee:import`, dan `employee:import:homebase`; organisasi memakai `organization:read`, `organization:read:homebase`, `organization:manage`, dan `organization:manage:homebase`; jejak audit memakai `audit:read` dan `audit:read:homebase`; penggajian memakai `payroll:read:any`, `payroll:read:homebase`, `payroll:read:self`, `payroll:manage`, `payroll:schedule`, dan `payroll:schedule:homebase`; kalender hari libur memakai `holiday:read` dan `holiday:manage`; dasbor metrik SLO memakai `slo:read`; status operasional antrean keluar memakai `ops:read`. Grant role dikonfigurasi di `cmd/server/policy.go` (definisi tunggal di `internal/policymatrix`) sesuai matriks di `docs/PRD.md` §11.

Permission berakhiran `:any` berarti akses lintas seluruh organisasi dan hanya diberikan kepada `admin`. Permission berakhiran `:homebase` berarti akses dibatasi pada unit penugasan principal beserta seluruh turunannya pada pohon `Homebase`; `operator` dan `atasan` memakai permission ini. Permission berakhiran `:self` hanya memberi akses ke record milik principal sendiri. Cakupan ditegakkan di lapisan aplikasi: daftar difilter dengan `listing.Options.ScopeHomebaseIDs`, setiap record diperiksa per-pegawai pada use case baca, ubah, dan arsip, unit organisasi diperiksa per-unit, slip gaji diperiksa terhadap unit pegawai pemiliknya, dan pegawai hasil impor operator ditempatkan pada unit penugasannya (template impor tidak memuat kolom unit). Operator hanya dapat membuat unit baru di bawah induk yang sudah berada dalam cakupan; unit akar hanya dapat dibuat oleh `admin`. Principal tanpa penugasan unit tidak melihat data pegawai, unit, slip gaji, maupun jejak audit apa pun.

**Batas yang belum terpenuhi:** ingestion presensi menerima sesi pengguna dengan permission `attendance:event:ingest` selain autentikasi perangkat (`X-Device-ID` + bearer token), sehingga endpoint itu belum hanya bisa diakses mesin. Perubahan role pegawai melalui `PUT /api/v1/employees/{id}/role` sudah berjejak audit (`employee.role.updated`).

## Modul penggajian

Slip gaji tersedia di `/api/v1/payroll/slips`. `GET` daftar dan detail slip, `POST /api/v1/payroll/slips/{payrollId}/payment` mencatat konfirmasi pembayaran (hanya `admin`).

Konfirmasi pembayaran dicatat pada tabel `pembayaran` yang menempel pada slip gaji, lalu slip ditandai `TERBAYAR` beserta `tanggalDibayar`, `konfirmasiPembayaranAt`, dan `konfirmasiOlehId`. Status slip pada skema acuan adalah `DRAF`, `TERBIT`, dan `TERBAYAR`; slip hanya dapat dibayar satu kali dan hanya dari status `TERBIT`.

Pencatatan pembayaran, antrean notifikasi gaji, dan jejak audit `payroll.payment.confirmed` ditulis dalam satu transaksi. Karena itu notifikasi gaji tidak pernah ada tanpa bukti pembayaran yang tersimpan, dan pengiriman ganda dicegah oleh kunci idempotensi outbox.

Konfirmasi pembayaran pada MVP dimasukkan manual oleh admin: admin mengisi referensi transaksi/rekapan bank, waktu, dan pengesah. Integrasi otomatis ke bank (REST dan websocket) disiapkan sebagai adapter lanjutan yang menulis bukti pembayaran ke tabel `pembayaran` lewat jalur transaksional yang sama; implementasinya menunggu kontrak API vendor dan tidak dibuat tanpa pemakaian.

### Jadwal gajian dan pemberitahuan slip H-1

Tanggal gajian bersifat tetap (1–28) per unit organisasi, diinput lewat `GET/PUT /api/v1/payroll/schedules` — `admin` untuk seluruh unit (`payroll:schedule`), `operator` hanya unit dalam cakupan penugasannya beserta turunannya (`payroll:schedule:homebase`). Nilai disimpan di tabel `jadwalGaji` (satu baris per unit).

Seluruh slip (status apa pun) pada unit yang punya jadwal gajian diberi pemberitahuan **satu hari kalender sebelum** tanggal gajian; periode slip yang dikirim adalah **periode bulan sebelumnya** (slip Juni dibayar 25 Juli). Tanggal H-1 dipakai tetap — tidak digeser karena jatuh pada Sabtu, Minggu, atau hari libur nasional; jadwal `payroll.notify` tetap pada `5 19 * * *` (02:05 WIB). Pemberitahuan berisi nama, periode, tautan, dan QR ke halaman **verifikasi publik slip** (`/verify/slip/{token}`, menampilkan hanya nama/periode/status, tanpa nominal); slip tanpa token (dibuat sebelum fitur ini tersedia) dilewati. Pemberitahuan adalah pemberitahuan **ketersediaan slip**, bukan bukti pembayaran: tidak pernah memuat nominal gaji dan tidak menyatakan gaji sudah dibayar. Pesan disimpan di outbox sebagai jenis `email.slip-tersedia` dengan kunci idempotensi `slip-available:{slipId}`, sehingga setiap slip hanya diberi satu pemberitahuan. Pekerjaan dijalankan oleh `cmd/jobsched` (`5 19 * * *` = 02:05 WIB) lewat antrean RabbitMQ `simpeg.jobs` dan tercatat sebagai aksi `payroll.notified`. QStash tidak dipakai (`DEC-102`). Notifikasi gaji ("gaji sudah masuk") tetap terpisah dan hanya boleh terkirim setelah konfirmasi pembayaran tersimpan.

### Kalender hari libur nasional

Kalender diisi dari penyedia api.co.id (`HOLIDAY_API_URL`, `HOLIDAY_API_KEY`; header `x-api-co-id`) dan disimpan di tabel `HariLibur`. `POST /api/v1/holidays/{year}/refresh` (permission `holiday:manage`, hanya admin) mengganti seluruh entri tahun yang diminta dalam satu transaksi bersama jejak audit `holiday.refreshed`; `GET /api/v1/holidays?year=` (permission `holiday:read`) selalu membaca tabel lokal dan tidak pernah bergantung pada penyedia. Entri disimpan untuk `type` `Public Holiday`, `National Holiday`, dan `Joint Holiday`; `Observance` dilewati. Kalender **tidak** mengubah tanggal gajian maupun pemberitahuan H-1. Bila `HOLIDAY_API_KEY` kosong, penyegaran menolak (`503`) dan kalender bersifat baca saja.

Seluruh nominal pada API ditulis sebagai Rupiah yang sudah diformat (`"Rp 4.250.000"`), dan periode ditulis sebagai `YYYY-MM` beserta label Bahasa Indonesianya.

## Jejak audit

Jejak audit ditulis lewat paket `internal/audit` dan bersifat **append-only** dari sisi kode aplikasi: backend tidak memiliki jalur hapus atau ubah pada entri yang sudah tertulis, dan hal itu dijaga tes yang memindai source backend. Satu-satunya penghapusan adalah retensi yang disetujui: `audit.Cleaner` menghapus entri yang lebih lama dari `AUDIT_RETENTION_DAYS` hari (default 90; `0` berarti tanpa pemotongan). Pekerjaan itu dijalankan terjadwal oleh RabbitMQ (`cmd/jobsched` → antrean `simpeg.jobs`) dan tercatat sebagai aksi `audit.cleaned`. Setiap entri memuat aktor, aksi, sasaran, keterangan minimal, unit cakupan (`unitId`), alamat IP, dan waktu — isi profil pegawai tidak pernah disalin.

Akses dibatasi per unit: `admin` membaca seluruh jejak, `operator` hanya membaca jejak unit penugasannya beserta turunannya. Setiap pembacaan yang mengembalikan entri dicatat kembali sebagai aksi `audit.accessed`; pembacaan kosong tidak dicatat agar tabel tidak membengkak.

Kolom `unitId` adalah perubahan skema acuan dan harus selalu diperbarui bersama model GORM dan migrasi (`backend/migrations/000003_audit_log_unit.sql`). Retensi sudah ditetapkan; arsip dan ekspor jejak belum ada.

Schema memerlukan migration SQL [000001_directory_crud.sql](migrations/000001_directory_crud.sql). Migration runner yang dipilih adalah Goose dengan konfigurasi di `.goose.yaml` (direktori `./migrations`, `DATABASE_URL` sebagai env required). Workflow deployment tersedia di `.github/workflows/deploy-migrations.yml` dan diperkuat (`DEC-046`), tetapi belum pernah dijalankan di GitHub. Migrasi telah diterapkan dan diuji terhadap database nyata (`postgres` dan `simpeg_perf`) hingga versi Goose 23. Jangan gunakan `AutoMigrate`; tinjau dan terapkan migration secara terkendali sebelum menjalankan versi backend ini.

## Daftar, filter, dan pengurutan

Seluruh endpoint daftar memakai parameter yang sama: `page` (default 1), `pageSize` (default 20, maksimum 100), `search`, `sort`, dan `order` (`asc`/`desc`). Nilai `sort` di luar allowlist resource ditolak dengan `400 invalid_query`. Kolom SQL ditentukan server melalui allowlist di `internal/directory/domain/list.go` dan `internal/payroll/domain/sort.go`; nilai mentah dari pengguna tidak pernah masuk ke klausa `ORDER`. Nama kolom camelCase harus ditulis dengan kutip ganda (`"createdAt"`) agar tidak difold menjadi huruf kecil oleh PostgreSQL. Kontrak parameter bersama ada di `internal/listing`.

Daftar kategori hanya mengembalikan kategori aktif. DTO audit memuat aktor, aksi, sasaran, keterangan minimal, dan waktu — isi profil pegawai tidak pernah disalin ke audit.

Eviden pengajuan cuti: `BERSALIN`, `SAKIT`, `SAKIT_BERKEPANJANGAN`, dan `IZIN_PENTING` wajib menyertakan eviden saat pengajuan dibuat dan dicek ulang saat approve. Bentuk eviden: `SURAT_DOKTER` (berkas + nomor + tanggal surat dokter, untuk sakit/melahirkan), `FOTO` (berkas + waktu tangkap), atau `LAINNYA` (waktu + keterangan, untuk harian). Kolom model: `jenisEviden`, `fileEvidenUrl`, `waktuEviden`, `catatanEviden` (kolom lama `fileSuratUrl` di-rename menjadi `fileEvidenUrl` lewat migrasi `000019_cuti_eviden.sql`).

Aturan: cuti tahunan 12 hari kerja per tahun; syarat masa kerja ≥ 1 tahun pada tanggal mulai cuti (tanggal masuk `user.tanggalMasuk`; bila kosong syarat dilewati); sisa maks **6 hari** dibawa ke tahun berikutnya, **hangus 30 Juni** tahun berjalan, penghitungan carry **lazy**; hari kerja dihitung Senin–Sabtu (Minggu dan libur nasional tidak dihitung); saldo dipotong saat pengajuan **disetujui** dalam transaksi yang sama. Cuti panjang ≤ 2 bulan; syarat masa kerja ≥ 6 tahun berturut-turut **atau** haji (`untukHaji`); tidak memblokir cuti tahunan tahun berjalan. Cuti bersalin: sub-jenis wajib (`subJenisBersalin`: `MELAHIRKAN` 3 bulan / `KEGUGURAN` 1,5 bulan), surat dokter wajib. Izin penting (hari kalender): menikah 7, menikahkan anak 4, istri melahirkan/keguguran 4, duka keluarga inti 2, duka keluarga lain 1. Cuti sakit berkepanjangan: persen gaji pokok berjalan 100/75/50/25/0 (bulan 1–4/5–8/9–12/13–16/>16); baris `PeriodeSakit` diisi otomatis saat pengajuan disetujui; **slip gaji pokok periode yang cocok dibayar sesuai persen berjalan**; keterangan tercatat di jejak audit. Pengajuan yang tumpang tindih dengan pengajuan MENUNGGU/DISETUJUI milik pegawai yang sama ditolak **409** (pra-pemeriksaan + atomik saat approve). Kesejahteraan (seragam, transport, makan, rekreasi, K3L) belum dimodelkan.

Manajemen dokumen pegawai/dosen: endpoint `GET/POST/PATCH/DELETE /api/v1/arsip{...}` (permission `arsip:read`/`arsip:create`/`arsip:update`/`arsip:archive`). Berkas diunggah langsung ke Cloudinary oleh klien; backend hanya menyimpan URL dan metadata berkas (`fileUrl`, `fileSize`, `mimeType`, `cloudinaryPublicId`). Setiap jenis dokumen memiliki aturan format MIME dan ukuran maksimal (lihat `docs/PRD.md` dan `docs/DECISIONS.md` DEC-047). Konfigurasi Cloudinary: `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` (`.env.example`). Nomor rekening (`BankRekening`) dan nama rekening (`BankAtasNama`) sudah tersedia pada tabel `user`. Timestamps `createdAt`/`updatedAt` disimpan UTC dan ditampilkan Asia/Jakarta. Migrasi `000020_arsip_dokumen_tambahan.sql` menambah jenis dokumen dan kolom metadata.

## Event presensi mesin

`POST /api/v1/attendance/events` menyimpan fakta tap ternormalisasi (`machineId`, PIN mesin, waktu RFC 3339 ber-offset, dan `idempotencyKey`). Waktu disimpan sebagai UTC dengan presisi milidetik. Retry identik mengembalikan event yang sama; key yang sama dengan PIN/waktu berbeda menghasilkan `409`. PIN hanya kunci pengguna eksternal, bukan relasi langsung ke `User`; endpoint tidak membuat status harian atau menerima payload vendor/biometrik, GPS, maupun foto.

Endpoint memakai sesi bearer yang sama dengan API lain dan permission `attendance:event:ingest`; grant ini saat ini hanya diberikan kepada role `admin`. Ini mengautentikasi pemohon API, bukan perangkat. Autentikasi/kredensial perangkat dan adapter Fingerspot Revo W-230N belum tersedia karena kontrak vendor belum ditemukan. Draft [000002_attendance_events.sql](migrations/000002_attendance_events.sql) belum diterapkan; zona waktu sumber perangkat, jaminan idempotency key, pemetaan PIN, dan retensi masih perlu diputuskan. Migration belum diterapkan atau diuji terhadap database nyata.

### Perkakas pengukuran terhadap dependensi nyata

`cmd/perfbench` mengukur backend terhadap PostgreSQL, Redis, dan SMTP sungguhan (pengukuran QStash pada §PERFORMANCE-BASELINE §6.1 bersifat historis). Perkakas ini adalah perkakas operator, bukan bagian dari jalur permintaan aplikasi, dan hanya membaca kredensial dari environment.

```bash
export DATABASE_URL="postgres://<user>:<sandi>@<host>:5432/<database>?sslmode=require"

go run ./cmd/perfbench seed     --employees=5000 --months=6 --audit=50000
go run ./cmd/perfbench schema
go run ./cmd/perfbench explain
go run ./cmd/perfbench latency  --iterations=40
go run ./cmd/perfbench e2e      --requests=400 --streams=16
go run ./cmd/perfbench e2e      --soak --duration=60s --streams=16
go run ./cmd/perfbench deps     --redis --smtp --count=100   # QStash tidak dipakai (DEC-102)
go run ./cmd/perfbench slo
```

| Subcommand | Kegunaan                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------- |
| `seed`     | Mengisi database uji dengan data sintetis (pegawai, unit, slip gaji, jejak audit).                      |
| `schema`   | Membandingkan kolom model GORM dengan kolom yang benar-benar ada di database target.                    |
| `explain`  | Menjalankan `EXPLAIN (ANALYZE, BUFFERS)` atas statement yang direkam saat repository produksi berjalan. |
| `latency`  | Mengukur distribusi latensi tiap skenario query.                                                        |
| `e2e`      | Menjalankan binari `cmd/server` asli lalu mengukurnya lewat HTTP.                                       |
| `deps`     | Mengukur beban Redis dan SMTP.                                                                          |
| `slo`      | Memanggil endpoint pemeriksaan SLO dengan signature QStash seperti callback sungguhan (historis; jadwal aktif lewat RabbitMQ). |

Perintah `deps` menyentuh layanan pihak ketiga. Uji Redis memakai namespace sendiri dan menghapus kuncinya. Uji SMTP mengirim email sungguhan; penerima bawaan adalah alamat akun SMTP sendiri agar uji beban tidak mengirimi pihak ketiga, dan dapat diganti lewat `PERFBENCH_SMTP_RECIPIENTS`.

Jalur volume tinggi dijaga jumlah statement-nya oleh pengujian:

- Impor massal pegawai memeriksa identitas dengan satu query per chunk 250 baris, bukan satu query per baris per kolom (`internal/directory/repository/gorm_import.go`).
- Jejak audit impor ditulis dengan satu statement multi-row lewat `audit.WriteBatch` (`internal/audit/audit.go`).
- Notifikasi penggajian diantrekan dengan satu statement lewat `outbox.EnqueueBatch` (`internal/outbox/gorm_store.go`).

Pengujian penjaga jumlah statement ada di `backend/tests/directory/repository/gorm_import_test.go` dan `backend/tests/payroll/repository/schedule_test.go`. Bentrok impor terhadap data yang sudah ada tetap dilaporkan per kolom (`email`, `nip`, `nidn`, `nidk`) beserta indeks baris yang tepat.
