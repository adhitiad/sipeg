# Frontend rules

## Stack and boundaries

- Frontend stack: TanStack Start (React + TanStack Router), shadcn/ui, TanStack Query, TanStack Table, and TanStack Store.
- Package manager and script runner: **Bun** (`bun`, `bunx`). Commit `bun.lock`; never commit `package-lock.json`, `yarn.lock`, or `pnpm-lock.yaml`.
- Keep the frontend independently buildable from the Go backend. Use the backend API as the source of persisted business data; do not duplicate business rules in client state.
- Keep handwritten source files at or below 387 lines; use the documented exception of at most 397 lines only when splitting harms cohesion. `css`/`scss`/`sass`/`json`/`toml`/`yaml`/`yml`/`md` are exempt (see `project.md`).
- Internationalisation lives in `src/i18n/`: dictionaries (`dictionary.ts`, `messages/ui.{id,en}.ts`, `messages/content.{id,en}.ts`), runtime (`locale.tsx` provider + `locale-store.ts` useSyncExternalStore binder, `locale-context.ts` hooks). Default locale is `id`; `en` is selectable in the header. `<LocaleProvider>` wraps the app in `__root.tsx`.
- Better Auth is embedded in the TanStack Start server (`src/lib/server/better-auth.ts`, catch-all `src/routes/api/auth/$.tsx`) against the shared PostgreSQL auth tables. Public self sign-up is disabled; accounts are provisioned by an administrator (`scripts/provision-accounts.ts` for disposable databases). Sonner (`src/components/AppToaster.tsx`) surfaces sign-in/sign-out feedback.
- Any auth work must load the `better-auth-best-practices` and `better-auth-security-best-practices` skills first.

## Scaffolding

The frontend already exists (`frontend/`, TanStack Start + Tailwind v4 + shadcn/ui). Do not re-run `@tanstack/cli create` or `shadcn init`; they would overwrite the configured setup. The scaffolding path below is recorded for reference only:

```bash
bunx @tanstack/cli@latest create
bun --bun run dev
bun --bun run build
bun --bun run preview
bunx shadcn@latest init -t start
bunx shadcn@latest add <component>
```

## shadcn/ui (init before writing any component)

Initialise shadcn/ui **before** writing any component or page, so `cn()`, the theme CSS variables, the path aliases, and the base dependencies already exist.

```bash
bunx shadcn@latest init -t start
bunx shadcn@latest add button
```

- The shadcn CLI's own documentation uses `pnpm dlx`/`npx`; `bunx` is npm-compatible and is the project convention. If a `bunx` invocation misbehaves, run the equivalent command with `npx --yes` and report the discrepancy instead of switching the whole project to another package manager.
- `init` detects TanStack Start from `@tanstack/react-start`, writes `components.json` and `src/lib/utils.ts`, and injects the theme into the stylesheet. For a monorepo use `init -t start --monorepo` and add components with `-c apps/web` from the root.
- `components.json` must use `"style": "new-york"` (`"default"` is deprecated), `"tailwind.cssVariables": true`, a `baseColor` from the supported list, and the five aliases `components`, `ui`, `lib`, `hooks`, `utils`. `style`, `baseColor`, and `cssVariables` **cannot be changed after init** — decide them before running it.
- On Tailwind CSS v4 leave `tailwind.config` empty in `components.json`; the `tailwindcss()` Vite plugin plus `@tailwindcss/vite` provide the configuration, and `tailwind.css` points at the stylesheet that imports Tailwind.
- Add components with `bunx shadcn@latest add <component>`. Components live in the repository as source and are edited directly; do not hand-write a component that shadcn/ui already provides, and do not add a second component library or a custom design system on top.

## TanStack Start and routing

- File-based routing lives in `src/routes/`. `src/routes/__root.tsx` is the root document shell and provider boundary; `src/router.tsx` exports `getRouter()`, which returns a **new router per request** — never a module-level singleton.
- `src/routeTree.gen.ts` is generated by the router plugin/bundler. Never edit it by hand.
- Define routes with `createFileRoute` and export the result as `Route`; the generator requires that exact export name.
- Public JSON API endpoints (for example the embedded Better Auth runtime) are server routes: `createFileRoute('/api/auth/$')({ server: { handlers: { ANY: ... } } })`. The handler must convert failures to JSON responses and must not leak stack traces to clients.
- Keep the server/client split explicit: `*.functions.ts` exports `createServerFn` wrappers, `*.server.ts` holds server-only helpers, and plain `.ts` holds client-safe types, schemas, and constants. Import Protection enforces this — development warns, the build fails on a violation.
- Use `createServerFn` for server-only logic (default method `GET`; pass `{ method: 'POST' }` for writes) and server routes for public or cross-origin endpoints. Import server functions statically; dynamic imports break the bundler's server-function extraction.
- If the app defines `src/start.ts`, add `createCsrfMiddleware()` explicitly — Start only installs it automatically when no `src/start.ts` exists.
- Control per-route rendering with the `ssr` option (`true`, `false`, `'data-only'`).

## TanStack Query (server state)

- Use Query for every read of persisted business data: fetching, caching, invalidation, and mutation workflows.
- **Create the `QueryClient` inside `getRouter()`, not at module scope.** Start builds one router per SSR request; a process-wide client can serve one requester's cached data to another.
- Give query keys a consistent, feature-oriented structure and include **every** server-owned value (page, page size, sort, order, filters) in the key. Invalidate or update affected keys after a successful mutation.
- On Query v5 use `placeholderData: keepPreviousData` and `isPlaceholderData`. The former `keepPreviousData` option and `isPreviousData` flag were removed in v5.
- Refresh or invalidate session and user state after sign-in, sign-out, account disablement, or a permission change.

## TanStack Table (data tables)

- The backend owns pagination, sorting, and filtering. Use the `manualPagination`, `manualSorting`, and `manualFiltering` options and pass the server's rows and `rowCount`; the `manual*` options only suppress the corresponding client-side row models, they never fetch.
- Own the `pagination` and `sorting` state in the component, wire `onPaginationChange`/`onSortingChange`, and reset `pageIndex` to 0 when sorting or filtering changes — `manualPagination` disables `autoResetPageIndex`, so the reset is the component's responsibility.
- Keep the table's sort and filter values within the allowlist the backend documents. Never send a raw column name; the backend rejects unknown values with `400 invalid_query`.
- Render the loading, empty, error, and success states explicitly. Do not show success before the API confirms the mutation.

## TanStack Store (shared client state)

- Use Store only for client state that must be shared across UI areas — UI preferences, filter selections, multi-step form drafts. Server data belongs to TanStack Query.
- Create stores outside React with `createStore`, then read them with `useSelector`. The React `useStore` hook is deprecated in favour of `useSelector`; omit the selector only when the component genuinely needs the whole value.
- Group related writes with `batch()` so subscribers run once with the final state, and use derived stores for values computed from other stores.
- Do not store authorization decisions in client state and never trust role values supplied by the browser. The Go backend is authoritative.

## API contract and access control

- Call the backend under the versioned prefix `/api/v1` (see `docs/openapi.yaml`). Do not call unversioned `/api/...` paths; the backend rejects them with `400 unversioned_path`.
- The backend's error shape is uniform: `{"error": {"code", "message", "requestId", "fields", "rows"}}`. Type the API payloads against the OpenAPI contract; prefer generated or contract-derived types.
- Session transport to the Go API is `Authorization: Bearer <token>`; the browser never sends cookies cross-origin (backend CORS does not allow credentials). The token lives in memory only (`src/lib/auth-token.ts`); never write it to localStorage/sessionStorage. `/api/v1/me` is the session probe.
- Local development calls the backend same-origin through the Vite proxy: set `VITE_API_BASE_URL=/api/v1` and `VITE_API_PROXY_TARGET=http://localhost:8080` in the shell environment. Without the proxy, use an absolute `VITE_API_BASE_URL` and register the origin in the backend `TRUSTED_ORIGINS`.
- Better Auth is reached at same-origin `/api/auth` by default; set `VITE_AUTH_BASE_URL` only for a runtime on a separate origin.
- Treat client-side route guards and hidden controls as navigation only; the Go backend remains authoritative for authentication and authorization.
- Use secure server-managed session handling. Do not expose session secrets, OAuth client secrets, or privileged tokens to browser bundles, and do not connect browser code directly to PostgreSQL.
- Never use Supabase service-role/secret keys, Upstash tokens, RabbitMQ credentials, or email-provider credentials in the client. Do not publish messages to RabbitMQ or send email from the browser; the backend owns payment confirmation and notification delivery.
- Do not duplicate backend business rules in the client. The unit-scope rules, permission matrix, and validation all live server-side.

## UI quality

- Product-facing copy is bilingual: Bahasa Indonesia (`id`, default) and English (`en`). All user-facing strings go through the dictionaries in `src/i18n/messages/`; do not hardcode literals in components. Fall back to Indonesian when a key is missing only during development — add the key to both catalogs in the same change.
- Use sonner (`toast`) for transient feedback: sign-in/sign-out outcomes, validation failures, and recoverable API errors. Do not build ad-hoc toast or alert components.
- The landing page, About, Privacy Policy, Terms of Service, and Terms of Reference are public. The workspace and other authenticated pages sit behind `RequireAuth`; guards are navigation aids, never access control.
- Preserve keyboard operation, visible focus, semantic labels, and responsive layouts.
- Avoid placeholder controls and fabricated employee data in production UI. Use clearly synthetic data in development and tests.
- Reuse existing shadcn/ui primitives and project styling conventions before adding anything new. Design tokens and usage guidance live in `DESIGN.md` (draft pending product-owner approval).

## Quality tooling (required)

Every frontend package installs this tooling at scaffold time and wires it into `package.json` scripts and CI. Bun stays the runner: run tools through `bun --bun run <script>` (or `bunx <tool>` when there is no script yet).

```bash
bun add -d vitest @vitest/coverage-v8 @testing-library/react @testing-library/jest-dom jsdom
bun add -d eslint @eslint/js typescript-eslint eslint-plugin-react-hooks eslint-plugin-react-refresh eslint-config-prettier
bun add -d prettier
bun add -d @playwright/test
bun add zod
```

Required scripts in `package.json`:

| Script      | Command              | Gate                         |
| ----------- | -------------------- | ---------------------------- |
| `typecheck` | `tsc --noEmit`       | Zero errors, always          |
| `lint`      | `eslint .`           | Zero errors and warnings     |
| `format`    | `prettier --write .` | CI runs `prettier --check .` |
| `test`      | `vitest run`         | Unit/component tests pass    |
| `e2e`       | `playwright test`    | E2E flows pass               |

Tool rules:

- **Vitest** is the unit and component test runner. Configure `environment: 'jsdom'`, include `src/test/**/*.test.{ts,tsx}`, and test routes, forms, tables, and permission states from the existing TanStack tests, not snapshots of internals. Unit test files live in `src/test/` (never next to routes); use `React.createElement` instead of JSX inside `.ts` test files.
- **ESLint** uses flat config (`eslint.config.js`) with typescript-eslint, `react-hooks`, and `react-refresh`. Add `eslint-config-prettier` last so Prettier owns formatting and ESLint owns correctness. Do not disable rules without a comment explaining why. `no-explicit-any` stays enabled with **no** file-type override; do not add one. The gate is zero errors and zero warnings.
- **TypeScript types and interfaces** owned by this project live in `src/lib/types/**.d.ts`. Exceptions: `z.infer` derivations stay beside their Zod schemas (`src/validations/**`), types derived from runtime literals stay beside their source (`src/i18n/dictionary.ts`), component props stay co-located with their component, and vendored shadcn/ui component types stay with those components. Do not declare new exported interfaces/types inside feature, route, or service modules.
- **`tsc --noEmit`** is the typecheck gate. It must pass with zero errors; do not silence it with `@ts-ignore` or by loosening `tsconfig.json`. `src/routeTree.gen.ts` and other generated files are excluded from hand-editing but included in typechecking.
- **Playwright** is the only E2E runner. Specs live in `e2e/**.spec.ts`. Configure `webServer` to start the app itself (dev or `bun --bun run preview`), run against local or staging with synthetic data only, and never against production or real employee data. Network to the backend and to `/api/auth/*` is stubbed with `page.route`; the E2E environment never uses real credentials or data.
- **Prettier** is the formatter of record for all frontend files; CI checks formatting, so run `bun --bun run format` before committing. Do not add a second formatter.
- **Zod** validates untrusted data at the boundaries: API responses typed against `docs/openapi.yaml`, form inputs before they reach the API, and URL/search-param state. **Simpan semua skema dan aturan validasi Zod di `src/validations/**`** (mis. `src/validations/schemas.ts` atau berkas per-domain), sebagai berkas `.ts` client-safe; turunkan tipe TypeScript dari skema (`z.infer`) di lokasi yang sama. Impor lewat alias `@/validations/...`. User-facing validation messages come from the i18n dictionaries (Indonesian and English), not from ad-hoc literals.

## Verification

- Test important route, form, table, and permission states. Ensure API failures are visible and recoverable.
- Before pushing, run the full frontend gate in this order: `bun --bun run format` (or `bunx prettier --check .`), `bun --bun run lint`, `bun --bun run typecheck`, `bun --bun run test`, `bun --bun run build`, and `bun --bun run e2e` for flows you touched. All six tools are release gates, not optional.
- Run the repository's configured typecheck, lint, and tests for the changed frontend area, using the Bun commands (`bun --bun run ...`).
- Verify the production build (`bun --bun run build`) after changes to routing, server functions, or the shadcn setup; Import Protection failures surface only at build time.
- `git commit`/`git push` happen only after the user says "ok commit"/"ok push" (see `agents/rules/project.md`). A green gate is not permission to commit.
