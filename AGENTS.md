# Instruksi agen — SIMPEG

SIMPEG adalah sistem informasi kepegawaian. Repo ini masih fondasi, bukan aplikasi siap jalankan end-to-end.

## Struktur repo

- `backend/` — HTTP API Go/GORM (module `simpeg/backend`, Go 1.27.4). Entry point: `backend/cmd/server/main.go`.
- `backend/cmd/perfbench/` — perkakas operator untuk pengukuran terhadap dependensi nyata (seed, schema, explain, latency, e2e, deps, slo). Perkakas ini hanya membaca kredensial dari environment dan tidak boleh memuat nilai rahasia di dalam repo. Menjalankan `perfbench e2e` atau `cmd/migrate` terhadap **pooler transaksi Supabase (port 6543)** membutuhkan DSN dengan `default_query_exec_mode=simple_protocol` (PgBouncer tidak meneruskan prepared statement pgx) dan ekspor `PII_ENCRYPTION_KEY` untuk server yang di-spawn (`perfbench e2e` warisi environment shell).
- `backend/migrations/` — sumber skema aplikasi dalam migrasi SQL Goose; backend memetakan tabel dengan GORM di `backend/internal/models`. Keberadaan migrasi tidak membuktikan bahwa migrasi sudah diterapkan pada database target.
- `backend/internal/slo/` — area Service Level Objective: `domain` (aturan dan perhitungan persentil), `app` (use case pemeriksaan dan alert), `repository` (port persistensi metrik), dan `collector.go` (pengoleki metrik dalam proses). Metrik disimpan di PostgreSQL, bukan Redis.
- `docs/` — `docs/PRD.md` (baseline produk; item proposed/open bukan persyaratan yang dikonfirmasi), `docs/openapi.yaml` (kontrak HTTP API OpenAPI 3.1), `docs/DECISIONS.md` (log keputusan: pemilik, tanggal, status), `docs/RUNBOOK.md` (tindakan operator saat insiden), `docs/IMPLEMENTATION-PLAN.md` (checklist status pekerjaan), `docs/THREAT-MODEL.md` (ancaman per area data dan dependency), `docs/PERFORMANCE-BASELINE.md` (hasil pengukuran performa, uji beban, dan uji soak beserta keterbatasannya), `docs/SECURITY-TEST-OWASP-2025.md` (hasil uji dinamis OWASP Top 10:2025 dengan ZAP, temuan terbuka, dan keterbatasannya), `docs/DYNAMIC-ROUTE-VERIFICATION.md` (verifikasi dinamis seluruh rute dan skenario IDOR pada DB disposable), `docs/STAGING-RELEASE-CHECKLIST.md` (checklist kesiapan staging dan gerbang rilis), `docs/UI-LOAD-TEST.md` (hasil uji beban UI lokal dan keterbatasannya), `docs/backup-restore-drill.md` (formulir dan checklist drill backup/restore).
- `observability/` — templat stack monitoring, alerting, dan log self-hosted berbiaya Rp 0 (Prometheus, Alertmanager, Grafana, Loki + Promtail, node-exporter, cAdvisor, blackbox-exporter, metrik RabbitMQ). Retensi log agregasi 30 hari. Templat ini belum terpasang di target produksi, jadi jangan ditulis seolah alerting sudah aktif.
- `scripts/` — perkakas operator untuk repo ini, misalnya `scripts/backup-restore-drill.ps1` (dump/restore/verifikasi ke target disposable). Perkakas membaca kredensial hanya dari environment (`SOURCE_DATABASE_URL`, `TARGET_DATABASE_URL`) dan tidak boleh memuat nilai rahasia di dalam repo.
- `backend/Dockerfile`, `docker-compose.yml` (stack backend: migrasi, penjadwal, API), dan `rabbitmq/` (stack broker RabbitMQ yang berdiri sendiri dengan jaringan `simpeg-broker`) — deployment docker/podman, lihat DEC-042.
- `agents/rules/` — `project.md`, `backend.md`, `frontend.md`, `architecture.md`. Baca sebelum mengubah kode; konvensi ini mengikat.
- `frontend/` — aplikasi TanStack Start + Bun (shadcn/ui, TanStack Query/Store/Table): landing page publik, masuk/keluar lewat Better Auth tertanam di server frontend pada `/api/auth/*`, bilingual Indonesia/English (`id` bawaan), tema light/dark (light bawaan), sonner. Autentikasi diverifikasi terhadap database uji disposable (`DEC-049`); desain UI masih draf menunggu persetujuan pemilik produk (`DESIGN.md`). Aturan frontend: `agents/rules/frontend.md`. Tidak ada file `opencode.json`.
- Frontend sudah ada di `frontend/`; ikuti `agents/rules/frontend.md` sebelum mengubahnya: komponen UI lewat `bunx shadcn@latest add <component>`, lockfile hanya Bun, tooling mutu wajib (Vitest di `src/test/**.test.ts`, ESLint, `tsc --noEmit`, Playwright di `e2e/**.spec.ts`, Prettier, Zod).

## Perintah pengembang (jalankan di `backend/`)

Format (menulis ulang file):

```bash
gofmt -w .
```

CI memeriksa format dengan `gofmt -l .` dan gagal jika ada file yang belum diformat — jalankan `gofmt -w .` sebelum push.

Verifikasi + tes + build (urutan CI):

```bash
go mod download
go mod verify
go vet ./...
go test ./...
go build ./...

```

Tes satu paket:

```bash
go test ./tests/httpserver/...
go vet ./internal/database/...
```

## Hal penting yang mudah terlewat

- `config.Load()` baca env melalui `os.Getenv` — tidak auto-load `.env`. Setel `DATABASE_URL` (dan `BETTER_AUTH_SECRET` untuk verifikasi JWT Better Auth) di lingkungan sebelum menjalankan server. `APP_ENV` default `development`; `PORT` default `8080`. Pada `APP_ENV=production` backend menolak start bila `BETTER_AUTH_SECRET` kosong/kurang dari 32 karakter/memuat pola bawaan, atau `TRUSTED_ORIGINS` kosong.
- CORS hanya mengizinkan origin dari `TRUSTED_ORIGINS`; wildcard ditolak. Kosong berarti tidak ada akses lintas origin.
- Batas laju per klien diterapkan `httpserver.RateLimiter` (in-memory per instance); endpoint autentikasi punya batas lebih ketat. Batas waktu statement database diterapkan lewat `DB_STATEMENT_TIMEOUT` pada context permintaan. Keduanya dikonfigurasi lewat env — lihat `backend/README.md`.
- Row Level Security diaktifkan default-deny pada seluruh tabel aplikasi lewat `backend/migrations/000004_row_level_security.sql`. Jangan menambahkan policy RLS tanpa persetujuan; policy harus mencerminkan cakupan organisasi pengguna. Migrasi itu sengaja tidak memakai FORCE agar backend (role pemilik tabel) tetap bisa diakses.
- Integrasi layanan pendukung memakai paket terpisah: `backend/internal/outbox` (antrean persisten di PostgreSQL), `backend/internal/qstash` (publisher + verifikasi signature raw body), `backend/internal/mq` (RabbitMQ untuk pekerjaan terjadwal self-hosted, lihat DEC-042), `backend/internal/notify` (SMTP), `backend/internal/cache` (Redis, cache-saja). Worker outbox berjalan di background bila SMTP dikonfigurasi. Jangan menambah kode yang tidak dipakai.
- Aturan yang ditegakkan kode dan tidak boleh dilanggar: notifikasi gaji tidak boleh memuat nominal (konstruktor `notify.SalaryPaidNotice` dan payload `notify.SalaryPaidPayload` tidak menerima parameter nominal) dan hanya boleh dikirim setelah pembayaran terkonfirmasi. Sumber konfirmasi sudah ada: modul penggajian (`internal/payroll`) menyimpan baris `pembayaran` yang menempel pada slip gaji, dan `notify.EmailDeliverer.Confirmations` memakai `payroll/app.Service.ConfirmedPayment`. Redis hanya untuk cache data referensi — kunci sesi, token, kredensial, penggajian, dan status pembayaran otomatis ditolak.
- Struktur backend memakai empat lapis per area bisnis: `domain` (aturan dan nilai tanpa I/O), `app` (use case yang memeriksa permission dan cakupan), `repository` (port persistensi + adapter GORM), dan `httpserver` (transport, DTO, middleware). Area direktori: `internal/directory/{domain,app,repository}`; area penggajian: `internal/payroll/{domain,app,repository}`. Kontrak daftar bersama ada di `internal/listing` (`listing.Options`). Jangan menaruh logika bisnis di handler; handler hanya menerjemahkan HTTP → use case dan error → status HTTP.
- Tes tidak butuh database nyata (handler pakai fake; tes `database` parsing skema GORM). `DATABASE_URL` hanya diperlukan untuk menjalankan server.
- Jangan pakai GORM `AutoMigrate` untuk skema. Migration runner dipilih: Goose (SQL berversi di `backend/migrations/`), dan workflow penerapannya ada di `.github/workflows/deploy-migrations.yml` (lihat DEC-033). Migrasi **sudah** diterapkan pada database Supabase `postgres` (23 versi Goose per 2026-11-13) dan pada database uji terpisah `simpeg_perf`; `000002_attendance_events.sql` sudah ikut terpasang bersama migrasi lain. Migrasi `000024_jabatan.sql` sudah ada dan diterapkan pada database disposable `simpeg_verify` (2026-11-13), belum pada produksi; migrasi `000025_payroll_core.sql` sudah disetujui (`DEC-068`, disetujui 2026-11-14) tetapi belum diterapkan pada database mana pun. Karena migrasi itu sudah terdaftar di repo, `migrate up` pada target mana pun akan menerapkannya — penerapannya wajib lewat workflow staging lebih dulu, lalu verifikasi `perfbench schema`, lalu produksi dengan persetujuan pemilik. Jangan menyimpulkan keadaan database dari isi repo — periksa `goose_db_version` pada database target. Kolom identitas PII `user.nik`, `user.nip`, `user.npwp`, `RiwayatPendidikan.noIjazah`, `KeluargaPegawai.nik` disimpan terenkripsi pada level aplikasi (`enc1:`, AES-256-GCM, nonce acak) dengan blind index HMAC-SHA256 untuk keunikan/kesetaraan (`nikHash`/`nipHash`/`npwpHash`/`noIjazahHash`; `keluargaPegawai."nikHash"` non-unik); kunci dari `PII_ENCRYPTION_KEY` (base64 32 byte), wajib pada production. Pencarian NIP/NIK keluarga bersifat kesetaraan persis; sort `nip`/`nik` tidak ada (DEC-053, DEC-054).
- Penggajian naik menjadi scope inti pada 2026-11-14 (`DEC-067`): komponen, kategori status, kontrak kerja, struktur yayasan, dan pensiun menjadi cakupan inti; aturan bisnis komponen ditetapkan pada `DEC-070` (2026-11-14), asumsi isi-kemungkinan dicatat pada `DEC-071`, skema `000025_payroll_core.sql` disetujui (`DEC-068`) tetapi belum diterapkan. Irisan 1–3 (`DEC-073`–`DEC-075`), potongan alpa (`DEC-076`), pipeline presensi (`DEC-077`), slip digital (`DEC-078`), aturan cuti (`DEC-079`–`DEC-082`), pemberhentian/perpanjangan (`DEC-083`), THR (`DEC-084`/`DEC-085`), master pensiun (`DEC-088`/`DEC-089`), dan baca Surat Keputusan (`DEC-091`) sudah diimplementasikan; rancangan yang masih menunggu keputusan pemilik (alur penerbitan SK, potongan koperasi/pinjaman, SP1 dari presensi) ada di `docs/USULAN-*.md`. Jangan menerapkan migrasi `000025`–`000032` sebelum workflow migrasi pada staging lebih dulu dan verifikasi `perfbench schema`.
- Endpoint yang butuh permission mengembalikan `403` bila role tidak punya grant (deny-by-default). `GET /api/v1/me` butuh header `Authorization: Bearer <session-token>`.
- Jika ada perubahan database, implementasikan struktur yang disetujui pada mapping GORM dan migrasi SQL Goose. Package `internal/models` menyediakan `models.All()` sebagai registry model; daftarkan model baru agar ikut pemeriksaan mapping. Tes database memeriksa tabel, indeks query kritis, dan cakupan migrasi RLS, tetapi tidak membuktikan migrasi sudah diterapkan atau seluruh kolom GORM sama dengan database target. Jalankan `go test ./tests/database/...` setelah mengubah model atau migrasi, dan `go run ./cmd/perfbench schema` untuk memeriksa keselarasan model dengan database target secara langsung.
- Keselarasan model dan skema harus diverifikasi terhadap database target, bukan disimpulkan dari kode. Model GORM menulis seluruh kolomnya pada `INSERT`, sehingga kolom yang dinyatakan model tetapi tidak ada pada tabel membuat setiap path yang menulis baris itu gagal. `docs/PERFORMANCE-BASELINE.md` §8 mencatat lima cacat yang ditemukan lewat pengukuran nyata, termasuk `pembayaran.updatedAt` yang membuat konfirmasi pembayaran gaji selalu gagal.
- Ukuran pool koneksi harus di bawah batas pooler penyedia. Pooler sesi Supabase membatasi jumlah koneksi concurrently per proyek; ketika `DB_MAX_OPEN_CONNS` melampaui batas itu, PostgreSQL menolak koneksi baru dengan `EMAXCONNSESSION` dan backend menjawab `503`. Bawaan repository adalah 10 koneksi.
- Backend memakai GORM dan migrasi Goose. Jangan gunakan GORM `AutoMigrate` untuk skema production. Status database harus diverifikasi melalui migrasi dan pemeriksaan database target, bukan disimpulkan dari kode model.
- Teks yang menghadap pengguna dan dokumentasi dalam Bahasa Indonesia; identifier kode dalam bahasa Inggris.
- Sumber kebenaran: keputusan/kebijakan produk yang disetujui ada di `docs/PRD.md` (khusus matriks akses: §11); checklist/status pekerjaan ada di `docs/IMPLEMENTATION-PLAN.md`; perilaku aktual harus diverifikasi pada konfigurasi entry point, middleware, dan handler backend. Jangan menyamakan persetujuan kebijakan dengan implementasi lengkap. Jika dokumen bertentangan dengan kode, laporkan dan perbaiki dokumentasi yang stale; jangan menambah grant atau mengklaim cakupan akses tanpa verifikasi route dan query.
- Status otorisasi saat ini: grant statis dikonfigurasi di `backend/cmd/server/policy.go` (definisi tunggal di `backend/internal/policymatrix`; matriks disetujui di `docs/PRD.md` §11). Permission berakhiran `:any` = lintas seluruh organisasi (khusus `admin`); permission berakhiran `:homebase` = dibatasi pada unit penugasan principal **beserta seluruh turunannya** pada pohon `Homebase` (`operator`, `atasan`); permission berakhiran `:self` = hanya record milik principal sendiri (`pegawai`). Cakupan ditegakkan di lapisan aplikasi pada data pegawai, unit organisasi, slip gaji, dan jejak audit: daftar difilter lewat `listing.Options.ScopeHomebaseIDs`, setiap record diperiksa per-pegawai, dan import operator menempatkan pegawai pada unit penugasannya. Operator hanya dapat membuat unit di bawah induk yang sudah berada dalam cakupan. Permission `audit:read` (admin) membuka `GET /api/v1/audit-logs` untuk seluruh jejak; `audit:read:homebase` (operator) hanya untuk unitnya; `category:read` membuka `GET /api/v1/categories`; `payroll:read:any`/`payroll:manage` (admin) membuka modul penggajian, `payroll:read:homebase` (operator) untuk unitnya, `payroll:read:self` (pegawai) untuk slipnya sendiri; `payroll:schedule` (admin, seluruh unit) dan `payroll:schedule:homebase` (operator, unitnya beserta turunannya) membuka `GET/PUT /api/v1/payroll/schedules`; `holiday:read` (admin, operator, atasan) membuka `GET /api/v1/holidays`; `holiday:manage` (admin) membuka `POST /api/v1/holidays/{year}/refresh`; `slo:read` (admin, `DEC-050`) membuka `GET /api/v1/admin/slo/metrics` dan halaman `/admin/slo` — hanya agregat per rute, bukan metrik mentah; `ops:read` (admin, `DEC-065`) membuka `GET /api/v1/admin/ops/status` — agregat outbox (jumlah per status, usia pesan tertua, kegagalan per jenis) tanpa payload/dedupe key/penerima; `pemberhentian:propose:any`/`pemberhentian:propose:homebase` (admin, operator per unit) membuka `POST /api/v1/pemberhentian`; `pemberhentian:read:any`/`:homebase` membuka `GET /api/v1/pemberhentian*`; `pemberhentian:approve` (admin) membuka `POST /api/v1/pemberhentian/{id}/approve|reject` dan **`GET /api/v1/pemberhentian/{id}/kompensasi-preview`** (pratinjau kompensasi baca-saja: masa kerja, pesangon aturan admin, tambahan 1 bulan/5 tahun, total — untuk ditampilkan sebelum keputusan) — **menyetujui pengajuan menonaktifkan pegawai (`aktif=false`)**; `perpanjangan:manage` (admin, kantor pusat, `DEC-083`) membuka `POST /api/v1/perpanjangan` — perjanjian baru yang tumpang tindih dengan kontrak AKTIF pegawai ditolak `409` kecuali dipaksa dengan `allowOverlap: true` (tercatat di jejak audit); `kontrak:read:any`/`:homebase`/`:self` membuka `GET /api/v1/kontrak`; `pesangon:manage` (admin) membuka `GET/POST/PATCH/DELETE /api/v1/pesangon-aturan*` (`DEC-083`); `pensiun:manage` (admin, `DEC-088`) membuka `GET/POST/PATCH/DELETE /api/v1/pensiun/konfigurasi*` dan `/api/v1/pensiun/kepesertaan*` (konfigurasi pensiun effective-dating per kategori status; kepesertaan DPLK per pegawai; `tanggalMulaiPensiun` dihitung dari tanggal lahir + BUP bila tidak diisi); `pensiun:read:homebase` (operator & atasan, `DEC-089`) membuka `GET` keduanya — **kepesertaan difilter di server pada cakupan unit principal beserta seluruh turunan**; konfigurasi adalah master referensi organisasi (tanpa filter unit); frontend menyembunyikan formulir/tombol tulis bagi pemegang read saja; hanya admin yang boleh menulis; `sk:read:any` (admin) membuka `GET /api/v1/surat-keputusan` & `GET /api/v1/surat-keputusan/{id}` — seluruh SK (termasuk SK-PHK otomatis dari persetujuan pemberhentian); `sk:read:homebase` (operator & atasan, `DEC-091`) membuka keduanya **hanya untuk SK pegawai pada cakupan unit principal beserta turunan** (SK di luar cakupan → `404`); modul SK **baca-saja** — penerbitan manual belum diputuskan (`docs/USULAN-ALUR-SURAT-KEPUTUSAN.md`); `thr:manage` (admin) membuka `GET/POST /api/v1/payroll/thr/config`, `DELETE /api/v1/payroll/thr/config/{tahun}`, `GET /api/v1/payroll/thr/plan` (rencana kandidat + yang dilewati, baca-saja) dan `POST /api/v1/payroll/thr/generate` (THR dibuat sebagai slip terpisah pada tanggal berlaku, **tanpa iuran apa pun**; sumber nominal dari slip `TERBIT`/`TERBAYAR` terakhir; `overrides` berisi nominal prorata yang diinput admin). **Generate slip (`payroll:manage`)**: slip untuk periode setelah bulan pemberhentian pegawai ditolak `409`; slip bulan pemberhentian memuat komponen penerimaan `PESANGON` (bulan kompensasi × gaji pokok berjalan) dan dikenakan TER bulan berjalan. **Jalur `DRAF → TERBIT`**: `POST /api/v1/payroll/slips/{payrollId}/terbit` (admin `payroll:manage`) — prasyarat konfirmasi pembayaran (`/payment` hanya untuk `TERBIT`); audit `payroll.slip.published`. **Slip `BATAL`** (dibatalkan saat approve pemberhentian untuk periode setelah bulan pemberhentian): tidak dapat digenerate ulang, dicetak, atau dikonfirmasi pembayarannya; tidak ditampilkan sebagai dibayar dan tidak masuk pembayaran riwayat penggajian. **Batas yang belum terpenuhi:** ingestion presensi menerima sesi pengguna dengan permission `attendance:event:ingest` selain autentikasi perangkat (`X-Device-ID` + bearer token), sehingga endpoint itu belum hanya bisa diakses mesin; perubahan role pegawai melalui `PUT /api/v1/employees/{id}/role` sudah berjejak audit (`employee.role.updated`). Tes cakupan: `backend/tests/httpserver/scope_handlers_test.go`, `backend/tests/httpserver/organization_scope_test.go`, `backend/tests/directory/app/employee_test.go`, `backend/tests/payroll/app/service_test.go`. Lihat `docs/PRD.md` §11 dan backend README sebelum mengubah izin atau menyatakan endpoint aman/tersedia.
- Jejak audit ditulis lewat paket `backend/internal/audit` dan bersifat **append-only** dari sisi kode aplikasi — tidak ada jalur hapus/ubah pada entri yang sudah tertulis; dijaga tes pemindai source. Satu-satunya penghapusan adalah retensi yang disetujui: `audit.Cleaner` menghapus entri yang lebih lama dari `AUDIT_RETENTION_DAYS` hari (default 90, `0` berarti tanpa pemotongan) dan pekerjaan itu dijalankan terjadwal lewat callback QStash. Setiap entri menyimpan `unitId` (unit cakupan saat aksi terjadi) sehingga akses audit dapat dibatasi per unit. Perubahan kolom ini perlu disinkronkan pada model GORM dan migrasi `backend/migrations/000003_audit_log_unit.sql`.
- Format error seragam di satu paket `backend/internal/apierror` (dipakai bersama oleh `auth` dan `httpserver`): `{"error":{"code","message","requestId","fields","rows"}}`. Gunakan `apierror.Code*`; jangan menulis bentuk error sendiri. Middleware `httpserver.JSONErrorMiddleware` mengubah 404/405 router menjadi JSON yang sama.
- Versi API memakai prefix path `/api/v1`. Konstanta `httpserver.APIPrefix` dan `httpserver.Version` — jangan hardcode `/api/...` di route atau tes; pakai `APIPrefix+"/..."`. Path tanpa versi ditolak `400 unversioned_path` oleh `VersionGuard`; versi tak dikenal `404`. Setiap respons memuat header `X-API-Version`. Versi naik hanya untuk perubahan yang merusak kompatibilitas.
- `/health` = liveness (selalu 200 saat proses hidup). `/ready` = readiness: memeriksa dependency wajib dengan timeout, mengembalikan 503 bila gagal, dan **tidak** membocorkan detail kegagalan. Jangan gabungkan keduanya.
- Log memakai `backend/internal/observability`: JSON satu baris per entri dengan correlation ID `X-Request-ID`. Header kredensial, body, dan nilai query string **tidak boleh** dicatat. Request ID dari klien hanya diterima bila karakternya aman, selain itu digenerate ulang.
- `docs/openapi.yaml` adalah sumber kebenaran kontrak rute. Per 16 November 2026 seluruh operasi yang terdaftar di backend terdokumentasi (**135 path, 231 operasi**, 0 hilang/ekstra, 0 `operationId` duplikat; kontrak direkonstruksi 2026-11-15 lalu diperluas saat pendaftaran rute master pensiun (`DEC-088`) dan baca SK (`DEC-091`)). Setiap rute baru wajib didokumentasikan di kontrak pada saat pendaftaran, lalu hitungan operasi diverifikasi ulang dengan membandingkan registrasi router (`backend/internal/httpserver/*.go`, `backend/cmd/server/main.go`) terhadap operasi OpenAPI.
- Observabilitas di luar aplikasi memakai templat `observability/` (stack self-hosted berbiaya Rp 0, `DEC-065`). Retensi log agregasi 30 hari dan terpisah dari `AUDIT_RETENTION_DAYS` serta `SLO_RETENTION_DAYS`. Status tersebut belum terbukti pada target produksi: pemasangan stack, wiring metrik/log, penerima alert, dan uji tembak alert masih menjadi pekerjaan operasi.
- Uji backup/restore memakai `docs/backup-restore-drill.md` (formulir hasil) dan `scripts/backup-restore-drill.ps1` (helper). Helper hanya membaca `SOURCE_DATABASE_URL` dan `TARGET_DATABASE_URL` dari environment, target wajib disposable dan tidak boleh menimpa database produksi. Kemampuan PITR mengikuti tier Supabase target (tier Free umumnya tidak setara PITR penuh), jadi klaim PITR hanya sah bila dibuktikan pada project tersebut.
- Sort dan filter daftar memakai `listing.Options` (`internal/listing`). Kolom sort berasal dari allowlist di sisi repository (`directory/domain/list.go`, `payroll/domain/sort.go`) — kolom SQL tidak boleh berasal dari input mentah. Nilai di luar allowlist ditolak `400 invalid_query`. Nama kolom camelCase harus dikutip ganda (`"createdAt"`) di SQL.
- **RBAC scoped (`DEC-087`–`DEC-089`):** matriks statis ada di satu sumber (`backend/internal/policymatrix`, dipakai `cmd/server/policy.go` **dan** `cmd/rbacseed`) — jangan menduplikasi daftar grant. Permission flat `<module>:<action>[:<scope>]` dipecah **hanya** lewat `rbac/domain.ParsePermission` (segmen terakhir `any|homebase|self` = scope; sisa segmen = module + action multi-segmen, mis. `skp:periode:read:any` → `skp` + `periode:read`). Aturan evaluator yang berlaku sekarang: (a) assignment ber-scope (`unitId`/`fakultasId`/`jurusanId`/`biroCode`) **tidak pernah** mengizinkan permintaan `:any`; (b) assignment tanpa scope mengizinkan `:any`; (c) `deniedPermissions` (blacklist) menutup grant pada base maupun bentuk ber-scope; (d) tier 1 (superadmin) dan tier 2 (operator induk) bypass matriks. Keputusan RBAC bersifat **otoritatif** bila principal punya assignment (termasuk penolakan — RBAC dapat mencabut grant statis); tanpa assignment, grant statis dipakai (migrasi bertahap). Cakupan data (homebase + turunan, `self`) ditegakkan di lapisan aplikasi/repository, bukan di evaluator.
- **Pemakaian `cmd/rbacseed`:** dry-run bawaan (tidak menulis apa pun); `--apply` menulis role/permission/matriks/assignment dalam satu transaksi dan **idempoten** (pengguna yang sudah punya assignment dilewati). Jalankan setelah migrasi `000032` terpasang di target dan **hanya** lewat prosedur rilis (`docs/RUNBOOK.md` §RBAC) — jangan pernah pada produksi tanpa persetujuan pemilik.
- **Verifikasi dinamis wajib untuk fitur yang menyentuh data:** gunakan database disposable (migrasi → seed sintetis → permintaan HTTP nyata → hapus database). Terapkan mutasi hanya pada database disposable; staging/produksi menunggu persetujuan pemilik dan verifikasi `goose_db_version`/`perfbench schema`.
- Mata uang sistem adalah Rupiah Indonesia (IDR) dan zona waktu operasional adalah Asia/Jakarta (UTC+7). Penyimpanan timestamp memakai UTC (`internal/timeutil`, `database.OpenPostgres` memaksa `timezone=UTC`), sedangkan tampilan dan aturan kalender memakai Asia/Jakarta. Nominal diformat dengan `internal/money` (`money.Format` → `Rp 1.500.000`); jangan menulis format angka sendiri dan jangan memakai simbol mata uang lain.
- Callback QStash tidak memakai sesi bearer. `POST /api/v1/internal/qstash/audit/cleanup` diverifikasi dengan signature HS256 atas raw body dan subjek yang harus cocok dengan URL tujuan (`qstash.Verifier`). Jadwal harian didaftarkan lewat `internal/jobs.EnsureSchedule` dan idempoten: jangan membuat jadwal kedua untuk tujuan yang sama. Pada deployment self-hosted (`RABBITMQ_URL` terisi), pendaftaran jadwal QStash dilewati dan pekerjaan berpindah ke RabbitMQ: penjadwal `backend/cmd/jobsched` menerbitkan pesan dan server mengonsumsinya lewat `internal/mq` (DEC-042). Bentuk endpoint QStash bersifat khusus: publish dan jadwal memakai destination pada path, sedangkan cron, percobaan ulang, dan metode pada header `Upstash-*`. `QSTASH_URL` boleh berisi root API regional; jalur `/v2/publish` dan `/v2/schedules` ditambahkan otomatis. Endpoint jadwal harus mengikuti region token.
- Transport SMTP mendukung TLS langsung (porta 465) dan STARTTLS (porta 587). Peningkatan ke TLS terjadi otomatis bila server menawarkannya dan selalu sebelum autentikasi. Bentuk `SMTP_FROM` berupa `"Nama Tampilan" <alamat@domain>` sah dan dipakai apa adanya pada header, sedangkan perintah `MAIL FROM` memakai alamat polosnya (`notify.SplitAddress`).
- DTO publik ada di `backend/internal/httpserver/directory_types.go`, `audit_handlers.go`, dan `payroll_handlers.go`; model GORM tidak boleh diekspos langsung sebagai skema API.
- Backend mendukung dua jenis sesi: JWT Better Auth (verifikasi via `BETTER_AUTH_SECRET` dengan `golang-jwt/jwt/v5`) dan sesi opaque GORM (database token), melalui `auth.CombinedSessionResolver` di `backend/internal/auth/jwt.go`. `POST /api/auth/logout` (daftarkan via `httpserver.RegisterLogoutRoute`) hanya mencabut sesi opaque GORM; penrevokasian token JWT tetap milik runtime Better Auth.
- Resolusi sesi membaca role dari tabel `Role` pada setiap permintaan, jadi perubahan role berlaku tanpa sesi baru; akun nonaktif dan baris `session` yang dihapus ditolak sebagai `401`. Status implementasi tabel `session`/`account`/`verification`/`twofactor` ada di `docs/PRD.md` §11.
- File sumber yang ditulis tangan maksimal 387 baris; batas mutlak 397 baris hanya dengan alasan yang terdokumentasi; lebih dari 397 harus dibagi. File generated dikecualikan.
- Jangan komit kredensial, token, atau data pribadi nyata. `.env` berada di `.gitignore`.

## CI

- `.github/workflows/backend.yml` berjalan pada push/PR: `go mod download`, `go mod verify`, `gofmt -l .`, `go vet`, `staticcheck`, `go test -race`, `go build`, `govulncheck`, dan pemindaian kebocoran connection string.
- `.github/workflows/frontend.yml` berjalan pada push/PR yang menyentuh `frontend/`: `bun install --frozen-lockfile`, `bun run format:check`, `bun run lint`, `bun run typecheck`, `bun run test`, `bun --bun run build`, dan `bun run e2e` (Playwright, Chromium). Vitest dijalankan dengan runtime Node karena runtime Bun 1.4.2 belum dapat menjalankan worker jsdom Vitest 5. Pengujian e2e **hibrida** (`frontend/e2e/hybrid-pemberhentian.spec.ts`) memakai backend + database disposable nyata (hanya autentikasi yang disimulasikan) dan **dilewati bila backend uji tidak hidup** — jalankan dengan backend dev + `VITE_API_PROXY_TARGET` agar proksi `/api/v1` aktif. Navigasi dalam e2e harus lewat klik tautan (bukan `page.goto`): token sesi disimpan di memori tab, sehingga muat ulang halaman mengeluarkan pengguna ke `/login`.
- Dependabot dijadwalkan mingguan untuk Go dan GitHub Actions (`.github/dependabot.yml`).
